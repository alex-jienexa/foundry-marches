# API: статус контракта

**Полного согласованного OpenAPI в приложенных материалах нет.** `openapi.yaml` намеренно не создан: пустой/выдуманный контракт вводил бы агентов в заблуждение.

В полных документах сохранены все примеры curl:

- [Foundry spike](../architecture/foundry.md) — примеры **внешнего relay**, не эндпоинты приложения;
- [WebDAV и Wiki](../architecture/obsidian.md) — предлагаемые операции синхронизации;
- [экспедиции](../architecture/expeditions.md) — предложенные маршруты, окончательные имена фиксируются на этапе 8;
- [фракции](../architecture/factions.md) — предлагаемые операции;
- [дорожная карта](../development/roadmap.md) — `/readyz`, RBAC, привязка персонажа и сценарии проверки этапов.

`FoundryGateway` в плане — эскиз интерфейса, не компилируемый Go-код. В §2.9 требуется `ApplyLevel`, которого ещё нет в эскизе §2.4; не игнорировать его при реализации.

Принцип исходного плана: OpenAPI генерируется из кода. На этапе 1 определить инструмент, правила совместимости и проверки; на каждом следующем этапе документировать фактические модели, права, статусы ошибок, идемпотентность, пагинацию и SSE/reconnect. Имена из curl не объявлять действующим API до реализации и согласования. Задача TASK-003 содержит этот пункт.
