## 0. Краткий итог

- ТЗ целостное и хорошо разбито на этапы. Ниже — места, где оно противоречит себе или правилам PF2e/Foundry, и решения по ним (раздел 1). Часть решений принята по вашим ответам, часть закрывается коротким Спайком 0.
- **Мост с Foundry.** Берём REST API модуль с relay, который вы разворачиваете у себя; Foundry остаётся на удалённом сервере. Relay не даёт идемпотентности и не знает PF2e, поэтому между приложением и relay стоит собственный адаптер с журналом операций. Кто чем владеет (Foundry или журнал приложения), описано в 2.7.

- **Экспедиции и фракции** встроены в общую модель: у них свои таблицы, но они опираются на карту, календарь, погоду, журнал транзакций и Wiki.
- **Схема БД** v0.3 лежит в `schema.sql`; 166 проверок в `schema_tests.sql` и 9 проверок гонок в `schema_race_tests.sh` закрывают замечания вашего ревью и внешнего аудита (5.1 и 5.4). Упавшая проверка теперь завершает прогон ошибкой.

### 1.2. Что в ТЗ уже сделано правильно

История без физического удаления, сторнирующие транзакции, права на сервере, автоматика без сюжетных решений, отдельное хранение секретов. Эти принципы сохранены и усилены: журнал аудита и журнал транзакций неизменяемы на уровне БД (триггеры), а не только на уровне кода.

## 2. Мост с Foundry VTT: что показало исследование

### 2.1. Устройство готового решения

Решение состоит из двух частей. Relay-сервер на Go принимает HTTP-запросы внешних клиентов, держит WebSocket-соединения с Foundry и управляет авторизацией, а модуль внутри Foundry работает в режиме «только GM», подключается к relay по WebSocket и выполняет вызовы Foundry API ([документация relay](https://foundryrestapi.com/docs)). Relay можно развернуть у себя: в документации есть docker-compose для самостоятельного размещения с SQLite ([quick start](https://foundryvtt-rest-api-relay.fly.dev/docs)). Публичный relay использовать не стоит — через него пройдут данные кампании.

### 2.2. Доступные возможности

Группы эндпоинтов: авторизация, холст, чат, список подключённых миров, эффекты, бои, универсальные операции над сущностями, события, файлы, макросы, плейлисты, броски, сцены, поиск, сессии, листы персонажей, структура мира и пользователи; отдельная группа системных эндпоинтов есть только для D&D 5e ([справочник API](https://robins-foundry-relay.duckdns.org/docs/api)). Для PF2e готовых эндпоинтов нет — значит, разбор данных PF2e (поля листа, монеты, XP) делаем мы.

Важное для нас:

- **Чтение и запись документов.** Есть получение сущности, обновление по UUID и выдача предмета (по UUID или по имени, с указанием количества) ([справочник по Entity](https://relay-shreddie.duckdns.org/docs/api/entity)). Выдача по имени ненадёжна — адаптер всегда использует UUID предмета из каталога.
- **События в реальном времени.** Через SSE можно подписаться на сообщения чата, броски и хуки Foundry (бои, акторы, сцены). Это основа для синхронизации «Foundry → приложение» при изменении листа.
- **Безопасность.** Запросы идут с ключом в заголовке и идентификатором мира в параметре. Ключи можно получать с ограниченными правами, например чтение и запись сущностей и поиск ([пример со scopes](https://glama.ai/mcp/servers/PhillypHenning/foundry-rest-api-mcp-server/tree)). Приложению выдаём ключ с минимумом прав, без прав на структуру мира, пользователей и файлы.
- **Работа без открытого браузера.** Есть управление «безголовыми» сессиями Foundry, а relay при включённой настройке сам запускает такую сессию, если целевой мир не в сети ([межмировые вызовы](https://robins-foundry-relay.duckdns.org/docs/cross-world-modules)). Для нас это путь к круглосуточной работе, но его нужно проверить на стабильность (Спайк 0).

### 2.3. Ограничения, которые надо закрыть своей логикой

1. **Нет идемпотентности.** Повторный `give` или `update` выполнится дважды.
2. **Нет транзакций.** Изменение монет — несколько вызовов.
3. **Нет знания PF2e.** Поля листа и структура монет разбираются нами.
4. **Пути зависят от версии relay.** В разных источниках встречаются разные формы путей для одних и тех же операций (с префиксом группы и без). Версия relay фиксируется, а все пути живут только в одном файле адаптера.
5. **Зависимость от GM-сессии.** Нет открытого мира — нет синхронизации.

### 2.4. Как адаптер закрывает ограничения

Порт `FoundryGateway` (интерфейс Go) не знает про relay:

```go
type FoundryGateway interface {
    Health(ctx) (WorldStatus, error)
    GetActorSnapshot(ctx, worldID, actorUUID string) (ActorSnapshot, error)
    ListChangedActors(ctx, worldID string, since time.Time) ([]string, error)
    ApplyXP(ctx, op XPOp) (XPResult, error)          // абсолютное значение + предусловие
    ApplyCoins(ctx, op CoinOp) (CoinResult, error)   // монеты как предметы
    GrantItem(ctx, op ItemOp) (ItemResult, error)    // только по UUID
    RemoveItem(ctx, op ItemOp) (ItemResult, error)
    SetActorOwner(ctx, op OwnerOp) error
    SubscribeActorChanges(ctx, worldID string) (<-chan ActorChange, error)
}
```

Правила выполнения любой записи:

- Каждая операция имеет `operation_id` (UUID) и живёт в таблице `integration_jobs` (видна мастеру, можно повторить или отменить).
- **Абсолютные значения вместо приращений.** Для XP: «было 3000 (предусловие) → станет 4000». Если на листе сейчас не 3000 — операция не выполняется, а уходит на проверку мастеру.
- **Метка выполнения на самом Actor.** В тот же вызов записи добавляется флаг модуля (`flags.westmarches.appliedOps`) с `operation_id`. Перед повтором адаптер читает флаг: если метка есть — операция считается выполненной, повторной записи нет.
- Для предметов: после выдачи читается Actor и проверяется, что предмет с нужным UUID-источником появился в нужном количестве.
- Подтверждение приходит только после чтения состояния назад. Пока его нет — покупка в магазине остаётся «в ожидании», как требует п. 8.3 ТЗ.

Ограничения этого механизма и как они закрыты:

- Флаг `appliedOps` на акторе хранит только последние 50 операций, чтобы лист не раздувался. Полный журнал и источник истины — таблица `integration_jobs`.
- Если флаг потерян или очищен, повтор всё равно безопасен. Для XP и уровня работает предусловие «было N» с абсолютным значением. Для предметов адаптер перед повтором ищет предмет с нужным UUID-источником и сверяет количество с ожидаемым (до + выдано). При сомнении операция получает статус «нужна проверка мастера», а не повторяется.
- Проверка в Спайке 0: стереть флаг у тестового актора и повторить операцию — результат не должен измениться.

### 2.5. Синхронизация «Foundry → приложение»

1. Подписка на хуки изменения Actor (SSE) — быстрый путь.
2. Периодическая сверка (по умолчанию раз в 10 минут) — страховка от пропущенных событий.
3. Сверка по запросу мастера.
4. Результат — новый `foundry_snapshot` и обновление полей персонажа; если изменились XP/монеты/предметы вне операций приложения — запись `external_adjustment`.

### 2.6. Спайк 0 (1–2 дня, до начала Этапа 2)

Цель — подтвердить гипотезы, на которых стоит Этап 2. Результат — короткий отчёт «подходит / нужен свой модуль».

| Проверка | Как проверяем | Критерий успеха |
| --- | --- | --- |
| Relay поднимается у нас | docker compose на VPS, подключение модуля из Foundry | `GET /clients` показывает мир |
| Чтение листа PF2e | `GET` сущности по UUID Actor | есть уровень, XP, HP, AC, скорость, предметы |
| Монеты — предметы? | чтение инвентаря тестового Actor | видны монетные предметы с количеством |
| Запись XP | `PUT` обновления с флагом операции | XP изменился, флаг записан, повтор не меняет |
| Уровень не меняется сам | добавить XP до порога | уровень остался прежним, на листе видна готовность |
| Выдача предмета по UUID из компендиума | `POST` выдачи | предмет в инвентаре с исходным UUID |
| Хуки | подписка SSE, правка листа в Foundry | событие приходит за секунды |
| Работа без браузера GM | безголовая сессия | запросы проходят, сессия переживает сутки |

Пример проверки (curl, форма запроса из документации relay):

```bash
curl -s "http://localhost:3010/structure?clientId=$CLIENT_ID&types=Actor" \
  -H "x-api-key: $FOUNDRY_API_KEY" | jq '.'
```

Если хотя бы две из трёх проверок «монеты / идемпотентная запись / стабильность безголовой сессии» провалены, переходим к варианту Б — собственному модулю **Foundry Bridge** (тонкий модуль с тем же портом `FoundryGateway`, всё остальное приложение не меняется).

### 2.7. Кто чем владеет

Foundry владеет состоянием листа, приложение — историей и намерениями. Расхождения не затираются, а записываются.

| Значение | Владелец | Как меняется | Расхождение |
| --- | --- | --- | --- |
| XP, уровень | Актор Foundry | только задачей интеграции: абсолютное значение и предусловие | запись `external_adjustment`, предупреждение мастеру |
| Монеты | Актор Foundry (монеты как предметы) | задача интеграции | то же; история хранится в журнале |
| Предметы инвентаря | Актор Foundry | выдача и удаление по UUID | сверка со снимком |
| Имя, портрет, родословная, класс, HP, AC, скорость, характеристики, навыки | Актор Foundry | приложение не пишет; зеркало обновляет только синхронизация | триггер БД запрещает любые другие записи |
| Статус, владелец, одобрение персонажа | Приложение | веб и бот | — |
| Свои валюты (репутация, жетоны, ресурсы фракций) | Журнал приложения | проводки | обратная проводка |
| Репутация у фракций, отношения, территории | Приложение | журналы с историей | обратная запись |
| Цены и остатки магазинов, очередь, экспедиции, припасы | Приложение | — | — |
| Статьи и журналы | БД, копии в Obsidian и Foundry | `rev` и хэш | запись конфликта |

Запись «изменить XP или деньги» всегда состоит из двух частей: проводка в журнале (что и зачем) и задача интеграции (применить к актору). Покупка считается завершённой только после подтверждения чтением назад.

### 2.8. Бюджет запросов и кэш

По вашим данным, в бесплатном плане публичного relay — 5000 запросов в месяц. При своём relay такого ограничения быть не должно, но в репозитории relay есть код биллинга ([структура проекта](https://robins-foundry-relay.duckdns.org/docs/contributing)), поэтому Спайк 0 проверяет, что локальный режим запросы не считает. Кэш нужен в любом случае: Foundry на удалённом сервере, а каждый вызов нагружает сессию GM.

1. Игроки читают только снимки из БД (`foundry_actors.snapshot`) и в Foundry не ходят: сколько бы ни было игроков, это 0 запросов.
2. Снимки обновляются по событиям SSE. Резервный опрос — раз в 10 минут и только по изменившимся актёрам (сравнение хэша).
3. Каталог предметов PF2e загружается один раз и обновляется при смене версии системы, а не по запросу пользователя.
4. Одинаковые одновременные запросы склеиваются; чтения журналов кэшируются на 5 минут.
5. Счётчик запросов по дням и предупреждение на 80% квоты, если лимит окажется включён. При исчерпании — режим «только очередь»: записи ждут, чтение идёт из кэша.

### 2.9. Повышение уровня и дополнения к Спайку 0

Когда XP достигает порога, приложение ставит `level_up_pending`, пишет игроку и мастеру в Discord и затем, по подтверждению мастера или автоматически (настройка), добавляет операцию `ApplyLevel` с предусловием «уровень сейчас N» и записью N+1. Вы ожидаете, что после программной смены уровня система оставит места для выбора черт. Как PF2e 8.7.0 ведёт себя в этом случае, я не проверял.

Спайк 0 дополняется проверками:

- поднять уровень тестовому актору через relay и посмотреть лист: появились ли пустые слоты черт, не сломались ли производные значения;
- подтвердить, что self-hosted relay не считает запросы по плану;
- подтвердить, что WebDAV-сервер отдаёт `ETag` и принимает `If-Match` (3.6);
- выгрузить образцы журналов Campaign Codex (3.2).

## 3. Obsidian и Campaign Codex

Приложение подключается к вашему готовому WebDAV как клиент и сводит три хранилища — Obsidian, БД и журналы Foundry. Плагин синхронизации не нужен.

### 3.1. Что изменилось в решении

- Сервер WebDAV уже настроен, поэтому приложение его не поднимает. В схеме `vault_credentials` (выдача доступа) заменены полями в `vaults`: адрес, корневая папка, логин, зашифрованный пароль, интервал опроса.
- Плагин (Remotely Save и подобные) не участвует: приложение само читает и пишет `.md`. Это снимает проблемы плагинов: в одном из описаний побеждает файл с более поздним временем изменения без слияния ([описание](https://github.com/scruel/obsidian-remotely-save)), а автосинхронизация идёт, только пока открыт Obsidian ([описание](https://github.com/ZeddYu/remotely-save)). Решения о конфликтах принимает приложение.

### 3.2. Campaign Codex

Модуль расширяет журнал Foundry особыми типами листов со связями, не заменяя обычные журналы, и проверен для Foundry 14 ([страница модуля](https://foundryvtt.com/packages/campaign-codex)). Как именно он хранит тип листа и связи, я не проверял, поэтому отображение связей до образцов не проектируем.

- **Спайк 0б.** Выгрузить через relay по 3–5 журналов каждого типа Codex и посмотреть JSON. По нему решаем, где лежат связи (флаги журнала или иное).
- **Целевое отображение.** Тип листа → `wiki_pages.type` и `foundry_journals.sheet_type`; связи Codex → `wiki_relations`.
- **Первый шаг только на чтение:** Foundry → приложение → Obsidian. Запись обратно в журнал включаем после спайка и сначала только для текста и названия.

### 3.3. Потоки данных

| Направление | Как работает | Защита |
| --- | --- | --- |
| Obsidian → приложение | worker раз в `sync_interval_sec` делает `PROPFIND`, сравнивает ETag с `vault_files.remote_etag`, скачивает изменённые `.md`, разбирает свойства заметки | `rev` и хэш, не время |
| Приложение → Obsidian | экспорт новой ревизии записью `PUT` с `If-Match` последнего ETag | ответ 412 = конфликт, файл не затирается |
| Foundry → приложение | хук изменения журнала (SSE) плюс периодическая сверка; HTML страницы журнала → Markdown | флаги `rev` и хэш в журнале |
| Приложение → Foundry | обновление текста журнала, Markdown → HTML | то же + права журнала по `visibility` |
| Obsidian ↔ Foundry | только через БД, прямой связи нет | один источник истины |

### 3.4. Свойства заметки

Обязательные: `id` (постоянный), `type`, `name`, `visibility`. Служебные, их пишет приложение: `rev`, `updated_at`. Остальные свойства уходят в `wiki_pages.attributes` и возвращаются в файл без потерь. Файл без `id` — новая страница; `id` записывается в файл при следующем экспорте. Какие свойства есть в ваших заметках, мне нужно увидеть на образце (вопрос в конце документа).

### 3.5. Конфликты и безопасность данных

1. Единица сравнения — `rev` и хэш содержимого.
2. `rev` файла равен `rev` в БД: правка принимается как новая версия (`source = obsidian`).
3. `rev` файла меньше: трёхстороннее слияние, базой служит версия из `wiki_versions`. Не вышло — в БД остаётся версия приложения, файл мастера сохраняется как `_conflicts/<id>.<время>.md`, создаётся запись `vault_conflicts` и уведомление.
4. Запись всегда с `If-Match`. Поддерживает ли ваш сервер условные запросы, проверяется в Спайке 0б; если нет, перед записью приложение перечитывает ETag и сравнивает хэш (слабее, но работает).
5. Удаление файла переводит страницу в «ожидает удаления»; действует порог массового удаления.
6. **Секреты.** Заметки мастера и страницы `gm_only` попадают только в vault мастера и в журналы, недоступные игрокам. В журналы Foundry с доступом игроков пишется только публичное содержимое. Правило прав журналов подтверждаем на вашем мире.
7. **Бюджет запросов к Foundry.** Журналы читаются пакетами и по событиям, а не опросом (см. 2.7).

### 4.4. Сквозные механизмы

1. **Журнал операций и события.** Бизнес-запись, строка `integration_jobs` и задача River создаются в одной транзакции; воркер выполняет; повтор безопасен (раздел 2.4). События для SSE, Discord и воркера пишутся в `event_outbox` (4.7).
2. **Журнал с двойной записью.** Транзакция — набор проводок с нулевой суммой; выпуск валюты идёт со служебного счёта `system`. Баланс меняется только при проведении транзакции, а `verify_account_balances()` сверяет его с проводками.
3. **Единая политика видимости** `CanSee(субъект, ресурс)` для wiki, карты, погоды, экспедиций и фракций. Фильтрация только на сервере: игроку скрытые гексы и страницы не отдаются вообще.
4. **Разрешения** проверяются в middleware и в сервисном слое. Боту не доверяем: он действует от имени пользователя, права пересчитывает сервер.
5. **Игровое время.** Все события привязаны к номеру игрового дня. Задача «наступил день N» запускает календарные и торговые события, смену погоды и расход припасов.
6. **Неизменяемость.** `audit_log`, проводки и таблицы `*_history` защищены триггером и отзывом прав: UPDATE и DELETE запрещены, исправление — обратной записью.
7. **Настройки кампании — данные**, а не код: лимит персонажей, разница уровней, срок предложения места, правила путешествий; с историей изменений.
8. **Реалтайм.** Изменение → запись в `event_outbox` → `NOTIFY` будит читателей → SSE. `NOTIFY` не хранит события, поэтому клиент после обрыва дочитывает пропущенное по `Last-Event-ID`.

### 4.5. Очередь записи на приключение

1. Заявка выполняется в транзакции с блокировкой строки приключения (`FOR UPDATE`).
2. Проверки: персонаж одобрен и активен; нет пересечения по времени; уровень в диапазоне; разница уровней подтверждённых участников вместе с кандидатом не больше `max_party_level_spread`; второй персонаж того же игрока не записан (если нет `allow_multi_char`).
3. Место есть и всё подходит → `confirmed` (или `pending_confirmation`, если мастер включил ручное подтверждение). Иначе → `queued` с `queued_at`.
4. При освобождении места выбирается кандидат по настраиваемому ключу (подходит по уровню → дольше ждёт → меньше недавних игр → раньше подана), прошедший те же проверки. Ему создаётся предложение с `offer_expires_at`. Кандидат, нарушающий разницу уровней, пропускается, но остаётся в очереди.
5. Задача воркера по истечении срока передаёт предложение следующему. Мастер может принять, переставить (`manual_order`) или исключить участника вручную.

### 4.6. Безопасность и развёртывание

- HTTPS через Caddy; Discord OAuth2 с `state` и PKCE; токены Discord шифруются, ключ лежит в отдельном секрете.
- Сессии: cookie `HttpOnly`, `SameSite=Lax`, CSRF-токен; ограничение частоты запросов; проверка подписи вебхуков.
- Секреты Foundry и Discord хранятся отдельно от пользовательских данных.
- `docker compose up -d` поднимает всё; миграции применяются при старте; есть `/healthz` и `/readyz`; восстановление из резервной копии — скриптом, проверка — на тестовой БД.

### 4.7. Очередь, журнал операций и события

У каждой части своя роль, иначе получатся две независимые системы управления задачами.

| Компонент | Ответственность |
| --- | --- |
| `integration_jobs` | Источник истины о каждой операции с внешней системой: что делать, предусловие, состояние, попытки, результат. Её видит мастер (повтор, отмена) |
| River | Только исполнитель. Задача в нём несёт лишь `job_id`, а вставляется в той же транзакции, что и строка `integration_jobs`. Состояние River нигде не считается истиной. Задачу, потерянную в River, подхватывает периодический sweeper по `state` и `next_attempt_at` |
| `event_outbox` | Журнал событий для SSE, Discord и воркера. Запись делается в той же транзакции, что и изменение; `NOTIFY` только будит читателей; после обрыва клиент читает события с `id` больше своего `Last-Event-ID` |

### 4.8. Защита исходящих запросов

Приложение само ходит в WebDAV и relay, поэтому адреса — потенциальные точки SSRF.

- Адреса `vaults.webdav_url` и `foundry_worlds.relay_url` задаёт только администратор, игрок передать адрес не может. Схема БД допускает для WebDAV только `https`.
- Перед каждым запросом имя разрешается в IP и проверяется (запрет loopback, link-local и частных сетей, кроме явно разрешённого внутреннего адреса relay); соединение идёт на проверенный IP, что закрывает DNS rebinding. Перенаправления отключены или проверяются заново.
- Разрешены только настроенные хосты и порты; есть таймауты и предел размера ответа.
- `remote_root` не может содержать `..` (ограничение в БД); пути нормализуются, выход за корень запрещён.
- Для `If-Match` годится только сильный ETag. Если сервер отдаёт слабый (`W/...`), приложение перечитывает ETag и сравнивает хэш.
- Пароль WebDAV и ключ relay хранятся зашифрованными, в журналы не попадают.

### 5.3. Что гарантирует БД, а что остаётся приложению

БД гарантирует: лимит персонажей, владельца заявки, статус приключения, места и разброс уровней, перекрытие по времени, неизменяемость журналов, баланс проводок и защиту баланса от прямой правки, зеркальность сторно, допустимые переходы состояний, запечатанный календарь, привязку к одной карте и одной экспедиции, автоматическую историю статусов, заявок, отношений, территорий и предприятия.

Приложению остаётся:

- брать `user_id` из сессии, а не из тела запроса (БД отвергнет чужого персонажа, но не подмену пользователя);
- выбирать, кому предложить освободившееся место, и ставить таймер предложения;
- переводить номер игрового дня в дату по версиям календаря;
- устанавливать `app.user_id`, `app.reason` и `app.writer` через `SET LOCAL` в начале транзакции;
- проверять права (`permissions`) и видимость (`CanSee`).

Разброс уровней считается по снимку `level_at_signup`. Он берётся из персонажа при заявке и не редактируется; мастер обновляет снимки функцией `recompute_signup_levels`, которая заново проверяет разброс. Автоматического пересчёта при повышении уровня нет (вопрос 9 в разделе 10).

## 6. Состояния и допустимые переходы

Переходы хранятся в таблице `state_transitions`; триггер отвергает всё, чего в ней нет. Начальное состояние — тоже переход «из ничего».

| Сущность | Начальные | Допустимые переходы |
| --- | --- | --- |
| Персонаж | черновик, ожидает одобрения, NPC | черновик → ожидает одобрения / архив; ожидает → активен / черновик (исправления) / архив; активен ↔ недоступен; активен или недоступен → умер / выведен / NPC; умер, выведен, NPC → активен (решение мастера) или архив |
| Заявка | в очереди, подтверждена, ожидает подтверждения | в очереди → предложено / подтверждена / отозвана / исключена / отклонена; предложено → подтверждена / отклонена / истекла / исключена / отозвана; подтверждена → отозвана / исключена; отозвана или истекла → в очереди (повторная запись) |
| Приключение | черновик, ожидает одобрения | черновик → ожидает / одобрено / отменено; ожидает → одобрено / черновик / отменено; одобрено → опубликовано; опубликовано → регистрация открыта; открыта ↔ закрыта; открыта или закрыта → проводится; проводится → завершено; отменено → черновик |
| Задача интеграции | ожидает | ожидает → выполняется / отменена; выполняется → успех / ошибка / ожидает (повтор) / ожидает синхронизации; ошибка или ожидает синхронизации → ожидает (ручной повтор) |
| Экспедиция | планирование | планирование → активна / прервана; активна → вернулась / прервана / провалена |

Если переход нужен, а его нет (например, воскрешение умершего персонажа мастером), он добавляется строкой в таблицу, а не обходом проверки. Политическое событие: черновик → применено → отозвано, а также черновик → отозвано; его эффект: ожидает → применено или ошибка, ошибка → ожидает, применено → возвращено. Событие нельзя применить, пока хоть один эффект не применён, и нельзя отозвать, пока хоть один применённый эффект не возвращён.

## 7. Система экспедиций

Экспедиция — поход партии из базы и обратно. Она занимает несколько игровых дней и может растянуться на несколько сессий, поэтому привязка к приключению необязательна.

### 7.1. Данные

| Таблица | Что хранит |
| --- | --- |
| `expeditions` | название, карта, ведущий персонаж, статус, гекс выхода и текущий гекс, плановые дни, игровые дни старта и конца, правила путешествия |
| `expedition_members` | состав: роль (штурман, разведчик, ответственный за припасы), скорость на момент входа, игровые дни входа и выхода. Один персонаж не может быть в двух активных экспедициях |
| `expedition_routes` | версии маршрута (путевые точки, плановые гексы, оценка дней); текущая версия одна |
| `expedition_legs` | один дневной переход: откуда, куда, пройденные гексы, часы в пути, бюджет движения, погода дня, модификаторы, итог |
| `expedition_supply_items` и `expedition_supply_ledger` | припасы (еда, вода, корм, свет, свои виды) и неизменяемый журнал их движения; остаток обновляется триггером |
| `expedition_events` | встречи, опасности, находки по дням |
| `expedition_visited_hexes` | история посещённых гексов: первый визит, число визитов, открыт ли туман |

### 7.2. Дневной переход

Это главная операция. Приложение предлагает результат, мастер подтверждает или правит: сюжетные решения автоматически не принимаются.

1. **Расчёт.** Бюджет движения = часы в пути × расстояние в час самого медленного участника ÷ размер гекса. Каждый гекс маршрута «стоит» множитель местности, к нему применяется множитель погоды дня (`terrain_types.travel_cost_mult`, `weather_types.travel_mult`).
2. **Предпросмотр.** Показывается, докуда дойдёт партия по маршруту, и сколько припасов уйдёт. Мастер может сдвинуть итог, добавить модификатор или пропустить день.
3. **Подтверждение.** В одной транзакции: запись `expedition_legs`; перенос партии на новый гекс; запись пройденных гексов; списание припасов не глубже остатка; продвижение игрового дня на 1 (настройка); предложение открыть туман на пройденных гексах (открывает мастер, запись идёт в `exploration_history`).
4. **Нехватка припасов.** Приложение не штрафует само: создаётся событие для мастера «припасы на исходе».
5. **Возвращение.** Приход в гекс с поселением предлагает перевести экспедицию в «вернулась», добавить запись в хронику и открыть окно наград.

Значения по умолчанию в `travel_rules` (подтвердите или поменяйте под ваши правила): 8 часов движения в день; расстояние в час = скорость в футах ÷ 10 (в милях); множители местности и погоды из справочников. Эти числа я взял по памяти, по книге правил не сверял.

Пример, если скорость самого медленного 20 футов, гекс 6 миль, равнина (множитель 1): 8 ч × 2 мили = 16 миль, около 2,7 гекса в день. В лесу (множитель 2) — около 1,3.

### 7.3. Проверка через curl (до интерфейса)

```bash
# создать экспедицию и состав
curl -s -X POST -H "Authorization: Bearer $GM" -H 'Content-Type: application/json' \
  -d '{"name":"К руинам","map_id":"'$MAP'","origin":[0,0],"members":["'$C1'","'$C2'"]}' $API/api/expeditions | jq .id

# версия маршрута
curl -s -X POST -H "Authorization: Bearer $GM" -d '{"waypoints":[[0,0],[1,0],[2,1],[3,1]]}' $API/api/expeditions/$E/routes

# предпросмотр дня, затем подтверждение (подтверждает только мастер)
curl -s -X POST -H "Authorization: Bearer $GM" $API/api/expeditions/$E/legs:preview | jq '{hexes_moved, supplies_used, warnings}'
curl -s -X POST -H "Authorization: Bearer $GM" -d '{"accept_preview":true}' $API/api/expeditions/$E/legs

# игрок не видит запланированного за пределами исследованного
curl -s -H "Authorization: Bearer $PLAYER" $API/api/expeditions/$E | jq '.route'
```

Это предлагаемые пути API; окончательные имена фиксируются в OpenAPI на этапе 8.

### 7.4. Видимость

Игрок видит состав, текущий гекс, пройденные гексы, свои припасы и опубликованные события. Он не видит запланированный маршрут за пределами исследованных гексов, заметки мастера и неразрешённые события. Это та же политика `CanSee`, что для карты и Wiki.

## 8. Система фракций

Фракции отвечают на четыре вопроса: как персонажи относятся к организации, как организации относятся друг к другу, кто чем владеет на карте и что изменилось в политике.

### 8.1. Данные

| Таблица | Что хранит |
| --- | --- |
| `factions` | организация: тип (фракция, государство, гильдия, культ…), связь со статьёй Wiki, родительская организация, цвет на карте, видимость, оценка силы |
| `faction_reputation_tiers` | ступени репутации (название, порог, бонусы); общая шкала и шкалы отдельных фракций |
| `faction_reputation_log` | неизменяемый журнал изменений репутации персонажа: сколько, почему, источник (приключение, экспедиция, предприятие, политическое событие), игровой день; ошибка исправляется обратной записью |
| `faction_reputation` | текущее значение; обновляется триггером из журнала |
| `faction_relations` и `faction_relation_history` | отношения пары организаций: положение от −100 до 100 и вид (союз, дружба, нейтралитет, напряжённость, соперничество, война, вассалитет с указанием старшей стороны) и полная история изменений |
| `territory_control` и `territory_history` | кто контролирует гекс (контролирует, оспаривает, влияет) и с какой силой; на гекс не больше одного «контролирующего» |
| `political_events` | политические события с набором эффектов; применяются мастером |

### 8.2. Как это работает

1. **Репутация.** Персональная, как в ТЗ («репутация персонажей»). Награда за приключение или экспедицию предлагает изменения репутации участникам, мастер подтверждает. Значение даёт ступень; ступень открывает или закрывает товары и магазины через `shop_requirements`.
2. **Отношения.** Хранятся одной строкой на пару (с упорядоченными идентификаторами, дубликатов нет). Любое изменение пишет строку истории с игровым днём и причиной.
3. **Территории.** Слой на карте: цвет фракции на контролируемых гексах, штриховка на оспариваемых. Игрок видит слой только на исследованных гексах и только для публичных фракций.
4. **Политические события.** Это основной инструмент перемен: событие собирает эффекты (изменить отношения, передать гекс, изменить репутацию) и применяется мастером одной транзакцией. Отмена не стирает историю, а создаёт обратные записи.

Пример набора эффектов:

```json
[
  {"op": "relation", "a": "<faction>", "b": "<faction>", "standing_delta": -30, "kind": "tense"},
  {"op": "territory", "map": "<map>", "hex": [3, 2], "faction": "<faction>", "control": "controlled", "strength": 70},
  {"op": "reputation", "faction": "<faction>", "scope": "adventure_participants", "delta": -5}
]
```

### 8.3. Правила автоматики

Приложение может предложить событие (например, «репутация у гильдии упала ниже порога — открыть конфликт?»), но не применяет его само. Это то же правило, что для торговых событий: сюжетные решения принимает мастер.

### 8.4. Проверка через curl

```bash
curl -s -X POST -H "Authorization: Bearer $GM" -d '{"character_id":"'$C1'","faction_id":"'$F'","delta":10,"reason":"спас караван"}' $API/api/factions/reputation
curl -s -H "Authorization: Bearer $PLAYER" $API/api/characters/$C1/reputation | jq '.[] | {faction, value, tier}'
# игрок не видит скрытую фракцию и её отношения
curl -s -H "Authorization: Bearer $PLAYER" $API/api/factions | jq 'map(.name)'
curl -s -X POST -H "Authorization: Bearer $GM" $API/api/political-events/$EV/apply | jq '{applied, history_rows}'
```

## 9. План этапов

Порядок внутри каждого этапа одинаков: сначала миграции и тесты БД, затем API с проверкой через curl, затем команда бота, и только после этого интерфейс. Этап закрывается, когда выполнены его проверки. Сроков я не ставлю: они зависят от вашего времени.

Порядок отличается от ТЗ в двух местах: добавлен Этап 0 (спайк), а экспедиции и фракции стоят после карт, календаря и погоды, на которые опираются, и перед торговым предприятием.

## 10. Вопросы к вам

1. Должен ли черновик персонажа занимать слот? Сейчас: нет, считаются «ожидает одобрения», «активен», «временно недоступен».
2. Пришлите образец заметки Obsidian со свойствами и структуру папок: по ним строится соответствие свойств и типов страниц.
3. Можно ли выгрузить 3–5 журналов каждого типа Campaign Codex в JSON (через relay или консоль Foundry)? Без этого связи не проектируем.
4. Правила путешествий: берём «скорость в футах ÷ 10 = миль в час, 8 часов в день» или у вас свои? Какой размер гекса в милях и сколько припасов в день на персонажа?
5. Репутация: диапазон и названия ступеней; персональная или общая на партию (сейчас персональная, а событие может применяться ко всем участникам приключения).
6. Видят ли игроки отношения между фракциями и границы территорий? Сейчас: только публичные фракции и только на исследованных гексах.
7. Повышение уровня: автоматически при достижении порога или после подтверждения мастера?
8. Нужен ли отдельный vault для игроков с публичными страницами, или игроки читают Wiki только в приложении?
9. Разброс уровней в группе считается по снимку на момент заявки, обновляемому мастером. Нужен ли автоматический пересчёт при повышении уровня персонажа?
10. Сейчас новые заявки принимаются только при статусе «регистрация открыта». Нужна ли предварительная запись в очередь на уже опубликованное приключение до открытия регистрации?
