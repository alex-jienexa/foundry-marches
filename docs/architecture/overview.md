# West Marches PF2e — архитектурный план, схема БД и этапы разработки

Версия 0.3 (учтены ваши уточнения и два раунда ревью схемы) · основа: ТЗ v1.0 + два дополнения (экспедиции, фракции) · язык документа: русский

## 0. Краткий итог

- ТЗ целостное и хорошо разбито на этапы. Ниже — места, где оно противоречит себе или правилам PF2e/Foundry, и решения по ним (раздел 1). Часть решений принята по вашим ответам, часть закрывается коротким Спайком 0.
- **Мост с Foundry.** Берём REST API модуль с relay, который вы разворачиваете у себя; Foundry остаётся на удалённом сервере. Relay не даёт идемпотентности и не знает PF2e, поэтому между приложением и relay стоит собственный адаптер с журналом операций. Кто чем владеет (Foundry или журнал приложения), описано в 2.7.
- **Obsidian.** Ваш WebDAV уже настроен, плагин не нужен: приложение само читает и пишет `.md`, разбирает свойства заметки и связывает их с журналами Foundry, включая Campaign Codex (раздел 3).
- **Стек:** Go + PostgreSQL 15+ + SolidJS/TypeScript, модульный монолит. River исполняет задачи, а источник истины об операциях — таблица `integration_jobs`; события живут в `event_outbox` (4.7).
- **Экспедиции и фракции** встроены в общую модель: у них свои таблицы, но они опираются на карту, календарь, погоду, журнал транзакций и Wiki.
- **Схема БД** v0.3 лежит в `schema.sql`; 166 проверок в `schema_tests.sql` и 9 проверок гонок в `schema_race_tests.sh` закрывают замечания вашего ревью и внешнего аудита (5.1 и 5.4). Упавшая проверка теперь завершает прогон ошибкой.

## 4. Архитектура

Модульный монолит на Go: один бинарь для API и воркера, отдельный процесс Discord-бота, PostgreSQL как единственное хранилище состояния и очередей.

&#91;embedded content: архитектура · 6 процессов, 3 внешние системы\]

Браузер приходит через Caddy в api, бот работает только через API, воркер ходит в Foundry через relay и в ваш WebDAV-сервер как клиент. У relay своя служебная база, а всё состояние кампании лежит в PostgreSQL.

### 4.1. Стек и обоснование

ТЗ разрешает альтернативы, поэтому ниже предложение под рабочий стек разработчика (Go, SolidJS, PostgreSQL). Архитектура от выбора языка не зависит.

| Компонент | Выбор | Почему | Вариант из ТЗ |
| --- | --- | --- | --- |
| Backend | Go, chi, pgx, sqlc | один бинарь, простое развёртывание на VPS, типизированный SQL | FastAPI / NestJS |
| Frontend | SolidJS + TypeScript + Vite | лёгкий, хорош для карты и форм; SSR не нужен — всё за логином | React / Next.js |
| БД | PostgreSQL | версия 15+: транзакции, JSONB, LISTEN/NOTIFY, частичные индексы, NULLS NOT DISTINCT | то же |

| Бот | discordgo, отдельный процесс | gateway-события (выход с сервера), slash-команды, кнопки | discord.py / discord.js |

### 4.2. Процессы

- **api** — HTTP API и SSE.
- **worker** — тот же бинарь, другая команда: задачи интеграций, WebDAV-клиент, генерация погоды, тики календаря, истечение предложений очереди.
- **bot** — Discord; не имеет своей БД, ходит в API с сервисным токеном.
- **relay** — Foundry REST API relay (свой экземпляр, готовый контейнер). Сам Foundry остаётся на вашем удалённом сервере.
- **postgres** (15+), **caddy**.

#### 4.2.1. Discord identity boundary (реализация первого bot-only этапа)

Discord Gateway — доверенная точка получения Discord identity. Бот принимает только guild-scoped interactions и извлекает Discord user ID, guild ID и актуальные member role IDs из payload DiscordGo. Он не принимает пользовательский ID из произвольного аргумента команды как доказательство личности.

Bot-to-backend запросы защищены отдельным случайным `DISCORD_BOT_API_TOKEN`; он не совпадает с `FOUNDRY_SYNC_API_TOKEN`. Бот доступен как отдельный Compose service и обращается к API по внутренней сети Compose. Backend повторно проверяет `DISCORD_GUILD_ID`, активную зарегистрированную Discord account и разрешение в PostgreSQL. Сервисный токен аутентифицирует процесс бота, а Discord identity в запросе является утверждением только этого доверенного процесса.

Регистрация открыта участникам единственного настроенного сервера. Новая учётная запись получает `player`; Discord IDs из `DISCORD_ADMIN_USER_IDS` получают `owner` при `/register`. Приложение хранит назначения ролей в `user_roles` и permissions в `role_permissions`; `discord_role_map` добавляет permissions по текущим member role IDs. Discord role mapping не может назначить `owner` или `admin` через bot commands; эти привилегии выдаются только доверенной конфигурацией/оператором БД.

Первый bot slice реализует регистрацию, просмотр несвязанных Foundry character Actors и существующих application characters, preview/confirmation привязки, grant `player`/`gm` и mapping Discord role → application role. Confirmation button привязана к инициатору и guild и истекает через 10 минут. Web OAuth2 и browser sessions отложены до появления браузерного интерфейса.

### 4.4. Сквозные механизмы

1. **Журнал операций и события.** Бизнес-запись, строка `integration_jobs` и задача River создаются в одной транзакции; воркер выполняет; повтор безопасен (раздел 2.4). События для SSE, Discord и воркера пишутся в `event_outbox` (4.7).
2. **Журнал с двойной записью.** Транзакция — набор проводок с нулевой суммой; выпуск валюты идёт со служебного счёта `system`. Баланс меняется только при проведении транзакции, а `verify_account_balances()` сверяет его с проводками.
3. **Единая политика видимости** `CanSee(субъект, ресурс)` для wiki, карты, погоды, экспедиций и фракций. Фильтрация только на сервере: игроку скрытые гексы и страницы не отдаются вообще.
4. **Разрешения** проверяются в middleware и в сервисном слое. Боту не доверяем: он действует от имени пользователя, права пересчитывает сервер.
5. **Игровое время.** Все события привязаны к номеру игрового дня. Задача «наступил день N» запускает календарные и торговые события, смену погоды и расход припасов.
6. **Неизменяемость.** `audit_log`, проводки и таблицы `*_history` защищены триггером и отзывом прав: UPDATE и DELETE запрещены, исправление — обратной записью.
7. **Настройки кампании — данные**, а не код: лимит персонажей, разница уровней, срок предложения места, правила путешествий; с историей изменений.
8. **Реалтайм.** Изменение → запись в `event_outbox` → `NOTIFY` будит читателей → SSE. `NOTIFY` не хранит события, поэтому клиент после обрыва дочитывает пропущенное по `Last-Event-ID`.

### 4.5. Очередь записи на приключение

1. Заявка выполняется в транзакции с блокировкой строки приключения (`FOR UPDATE`).
2. Проверки: персонаж одобрен и активен; нет пересечения по времени; уровень в диапазоне; разница уровней подтверждённых участников вместе с кандидатом не больше `max_party_level_spread`; второй персонаж того же игрока не записан (если нет `allow_multi_char`).
3. Место есть и всё подходит → `confirmed` (или `pending_confirmation`, если мастер включил ручное подтверждение). Иначе → `queued` с `queued_at`.
4. При освобождении места выбирается кандидат по настраиваемому ключу (подходит по уровню → дольше ждёт → меньше недавних игр → раньше подана), прошедший те же проверки. Ему создаётся предложение с `offer_expires_at`. Кандидат, нарушающий разницу уровней, пропускается, но остаётся в очереди.
5. Задача воркера по истечении срока передаёт предложение следующему. Мастер может принять, переставить (`manual_order`) или исключить участника вручную.

### 4.6. Безопасность и развёртывание

- HTTPS через Caddy; Discord OAuth2 с `state` и PKCE; токены Discord шифруются, ключ лежит в отдельном секрете.
- Сессии: cookie `HttpOnly`, `SameSite=Lax`, CSRF-токен; ограничение частоты запросов; проверка подписи вебхуков.
- Секреты Foundry и Discord хранятся отдельно от пользовательских данных.
- `docker compose up -d` поднимает всё; миграции применяются при старте; есть `/healthz` и `/readyz`; восстановление из резервной копии — скриптом, проверка — на тестовой БД.

### 4.7. Очередь, журнал операций и события

У каждой части своя роль, иначе получатся две независимые системы управления задачами.

| Компонент | Ответственность |
| --- | --- |
| `integration_jobs` | Источник истины о каждой операции с внешней системой: что делать, предусловие, состояние, попытки, результат. Её видит мастер (повтор, отмена) |
| River | Только исполнитель. Задача в нём несёт лишь `job_id`, а вставляется в той же транзакции, что и строка `integration_jobs`. Состояние River нигде не считается истиной. Задачу, потерянную в River, подхватывает периодический sweeper по `state` и `next_attempt_at` |
| `event_outbox` | Журнал событий для SSE, Discord и воркера. Запись делается в той же транзакции, что и изменение; `NOTIFY` только будит читателей; после обрыва клиент читает события с `id` больше своего `Last-Event-ID` |

### 4.8. Защита исходящих запросов

Приложение само ходит в WebDAV и relay, поэтому адреса — потенциальные точки SSRF.

- Адреса `vaults.webdav_url` и `foundry_worlds.relay_url` задаёт только администратор, игрок передать адрес не может. Схема БД допускает для WebDAV только `https`.
- Перед каждым запросом имя разрешается в IP и проверяется (запрет loopback, link-local и частных сетей, кроме явно разрешённого внутреннего адреса relay); соединение идёт на проверенный IP, что закрывает DNS rebinding. Перенаправления отключены или проверяются заново.
- Разрешены только настроенные хосты и порты; есть таймауты и предел размера ответа.
- `remote_root` не может содержать `..` (ограничение в БД); пути нормализуются, выход за корень запрещён.
- Для `If-Match` годится только сильный ETag. Если сервер отдаёт слабый (`W/...`), приложение перечитывает ETag и сравнивает хэш.
- Пароль WebDAV и ключ relay хранятся зашифрованными, в журналы не попадают.
