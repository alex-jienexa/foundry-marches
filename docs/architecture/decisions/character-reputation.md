# ADR — Репутация персонажа в вестмарше

- Статус: принято для будущей реализации
- Область: доменная модель приложения Foundry Marches
- Реализация: отложена до этапа разработки приложения

## Контекст

В PF2e Actor присутствует блок `system.pfs`, включая `system.pfs.reputation` с фиксированными кодами фракций Pathfinder Society (EA, GA, HH, VS, RO, VW). Эти поля принадлежат модели Pathfinder Society и управляются системой PF2e.

Вестмаршу нужна собственная система репутации, не ограниченная набором фракций PFS. Репутация должна отражать отношения конкретного персонажа с организациями, поселениями и другими сущностями игрового мира.

## Решение

1. Репутация является характеристикой **отдельного персонажа**, а не игрока/аккаунта. У разных персонажей одного игрока могут быть разные значения.
2. Данные PFS можно использовать как концептуальный ориентир и источник совместимых сведений там, где это уместно, но нельзя считать `system.pfs.reputation` основным хранилищем репутации вестмарша.
3. Основное состояние репутации и её история хранятся в базе данных приложения Foundry Marches.
4. `system.pfs` не переиспользуется для произвольных фракций вестмарша и не перезаписывается приложением.
5. При необходимости можно предусмотреть необязательную проекцию/синхронизацию данных в собственное пространство Foundry Actor flags, например `flags.foundry-marches.reputation`. Такая копия не является источником истины; детали синхронизации определяются при реализации.

## Предварительная модель данных

Это концептуальная структура для будущего проектирования схемы БД, а не утверждённая миграция:

- `reputation_factions` — организации, фракции, поселения и другие объекты репутации;
- `character_reputation` — текущее значение репутации конкретного персонажа у конкретного объекта;
- `reputation_events` — журнал изменений с величиной изменения, причиной, временем и источником;
- `reputation_ranks` — настраиваемые уровни/пороги репутации и их названия.

Связь репутации должна включать идентификатор персонажа и идентификатор объекта репутации. История изменений должна сохраняться отдельно от текущего агрегированного значения.

## Что ещё определить при реализации

- шкалу репутации, допустимые границы и правила начисления/снижения;
- набор типов объектов репутации и возможность репутации с NPC;
- ранги, пороги и игровые эффекты каждого ранга;
- правила модерации, ручной корректировки и аудита;
- идентификаторы и жизненный цикл персонажей при синхронизации с Foundry;
- формат, направление и конфликтную политику необязательной синхронизации Actor flags;
- окончательную схему БД и API.

## Последствия

- Репутация остаётся независимой от PFS и может расширяться под правила конкретного вестмарша.
- Персонажи одного игрока не наследуют репутацию друг друга автоматически.
- История изменений позволяет объяснять текущее значение и проводить аудит.
- На текущем этапе это только зафиксированное архитектурное решение: код, таблицы БД, API и Foundry flags не реализуются в рамках интеграционного spike.
