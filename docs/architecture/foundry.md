> **Действующее архитектурное решение (2026-11-25):** Foundry — единственный источник истины для Actor и PF2e-механик. Интеграция приложения через Relay read-only. Единственное исключение — отдельные GM-authorized операции добавления/удаления Item на существующем Actor, с проверкой прав, аудитом, идемпотентностью и read-back. Запись XP, уровня, валюты, характеристик, ownership и любых произвольных Actor-полей запрещена. Это решение из [ADR-0003](../../.agent/decisions/ADR-0003-foundry-authority-and-read-only-relay.md) имеет приоритет над любым противоречащим историческим текстом ниже.

> **Важно:** последующие разделы — сохранённый исторический импортированный материал. Все фрагменты, описывающие запись XP/level/coins/ownership, общий Relay write interface, запись документов Foundry или обратную синхронизацию в Foundry, не являются действующей архитектурой и отменены ADR-0003. Единственная поддерживаемая запись — узкие Item add/remove операции по отдельной задаче TASK-019.

## 2. Мост с Foundry VTT: что показало исследование

### 2.1. Устройство готового решения

Решение состоит из двух частей. Relay-сервер на Go принимает HTTP-запросы внешних клиентов, держит WebSocket-соединения с Foundry и управляет авторизацией, а модуль внутри Foundry работает в режиме «только GM», подключается к relay по WebSocket и выполняет вызовы Foundry API ([документация relay](https://foundryrestapi.com/docs)). Relay можно развернуть у себя: в документации есть docker-compose для самостоятельного размещения с SQLite ([quick start](https://foundryvtt-rest-api-relay.fly.dev/docs)). Публичный relay использовать не стоит — через него пройдут данные кампании.

### 2.2. Доступные возможности

Группы эндпоинтов: авторизация, холст, чат, список подключённых миров, эффекты, бои, универсальные операции над сущностями, события, файлы, макросы, плейлисты, броски, сцены, поиск, сессии, листы персонажей, структура мира и пользователи; отдельная группа системных эндпоинтов есть только для D&D 5e ([справочник API](https://robins-foundry-relay.duckdns.org/docs/api)). Для PF2e готовых эндпоинтов нет — значит, разбор данных PF2e (поля листа, монеты, XP) делаем мы.

Важное для нас:

- **Чтение и запись документов.** Есть получение сущности, обновление по UUID и выдача предмета (по UUID или по имени, с указанием количества) ([справочник по Entity](https://relay-shreddie.duckdns.org/docs/api/entity)). Выдача по имени ненадёжна — адаптер всегда использует UUID предмета из каталога.
- **События в реальном времени.** Через SSE можно подписаться на сообщения чата, броски и хуки Foundry (бои, акторы, сцены). Это основа для синхронизации «Foundry → приложение» при изменении листа.
- **Безопасность.** Запросы идут с ключом в заголовке и идентификатором мира в параметре. Ключи можно получать с ограниченными правами, например чтение и запись сущностей и поиск ([пример со scopes](https://glama.ai/mcp/servers/PhillypHenning/foundry-rest-api-mcp-server/tree)). Приложению выдаём ключ с минимумом прав, без прав на структуру мира, пользователей и файлы.
- **Работа без открытого браузера.** Есть управление «безголовыми» сессиями Foundry, а relay при включённой настройке сам запускает такую сессию, если целевой мир не в сети ([межмировые вызовы](https://robins-foundry-relay.duckdns.org/docs/cross-world-modules)). Для нас это путь к круглосуточной работе, но его нужно проверить на стабильность (Спайк 0).

### 2.3. Ограничения, которые надо закрыть своей логикой

1. **Нет идемпотентности.** Повторный `give` или `update` выполнится дважды.
2. **Нет транзакций.** Изменение монет — несколько вызовов.
3. **Нет знания PF2e.** Поля листа и структура монет разбираются нами.
4. **Пути зависят от версии relay.** В разных источниках встречаются разные формы путей для одних и тех же операций (с префиксом группы и без). Версия relay фиксируется, а все пути живут только в одном файле адаптера.
5. **Зависимость от GM-сессии.** Нет открытого мира — нет синхронизации.

### 2.4. Как адаптер закрывает ограничения

Порт `FoundryGateway` (интерфейс Go) не знает про relay:

```go
type FoundryGateway interface {
    Health(ctx) (WorldStatus, error)
    GetActorSnapshot(ctx, worldID, actorUUID string) (ActorSnapshot, error)
    ListChangedActors(ctx, worldID string, since time.Time) ([]string, error)
    ApplyXP(ctx, op XPOp) (XPResult, error)          // абсолютное значение + предусловие
    ApplyCoins(ctx, op CoinOp) (CoinResult, error)   // монеты как предметы
    GrantItem(ctx, op ItemOp) (ItemResult, error)    // только по UUID
    RemoveItem(ctx, op ItemOp) (ItemResult, error)
    SetActorOwner(ctx, op OwnerOp) error
    SubscribeActorChanges(ctx, worldID string) (<-chan ActorChange, error)
}
```

Правила выполнения любой записи:

- Каждая операция имеет `operation_id` (UUID) и живёт в таблице `integration_jobs` (видна мастеру, можно повторить или отменить).
- **Абсолютные значения вместо приращений.** Для XP: «было 3000 (предусловие) → станет 4000». Если на листе сейчас не 3000 — операция не выполняется, а уходит на проверку мастеру.
- **Метка выполнения на самом Actor.** В тот же вызов записи добавляется флаг модуля (`flags.westmarches.appliedOps`) с `operation_id`. Перед повтором адаптер читает флаг: если метка есть — операция считается выполненной, повторной записи нет.
- Для предметов: после выдачи читается Actor и проверяется, что предмет с нужным UUID-источником появился в нужном количестве.
- Подтверждение приходит только после чтения состояния назад. Пока его нет — покупка в магазине остаётся «в ожидании», как требует п. 8.3 ТЗ.

Ограничения этого механизма и как они закрыты:

- Флаг `appliedOps` на акторе хранит только последние 50 операций, чтобы лист не раздувался. Полный журнал и источник истины — таблица `integration_jobs`.
- Если флаг потерян или очищен, повтор всё равно безопасен. Для XP и уровня работает предусловие «было N» с абсолютным значением. Для предметов адаптер перед повтором ищет предмет с нужным UUID-источником и сверяет количество с ожидаемым (до + выдано). При сомнении операция получает статус «нужна проверка мастера», а не повторяется.
- Проверка в Спайке 0: стереть флаг у тестового актора и повторить операцию — результат не должен измениться.

### 2.5. Синхронизация «Foundry → приложение»

1. Подписка на хуки изменения Actor (SSE) — быстрый путь.
2. Периодическая сверка (по умолчанию раз в 10 минут) — страховка от пропущенных событий.
3. Сверка по запросу мастера.
4. Результат — новый `foundry_snapshot` и обновление полей персонажа; если изменились XP/монеты/предметы вне операций приложения — запись `external_adjustment`.

### 2.6. Спайк 0 (1–2 дня, до начала Этапа 2)

Цель — подтвердить гипотезы, на которых стоит Этап 2. Результат — короткий отчёт «подходит / нужен свой модуль».

| Проверка | Как проверяем | Критерий успеха |
| --- | --- | --- |
| Relay поднимается у нас | docker compose на VPS, подключение модуля из Foundry | `GET /clients` показывает мир |
| Чтение листа PF2e | `GET` сущности по UUID Actor | есть уровень, XP, HP, AC, скорость, предметы |
| Монеты — предметы? | чтение инвентаря тестового Actor | видны монетные предметы с количеством |
| Запись XP | `PUT` обновления с флагом операции | XP изменился, флаг записан, повтор не меняет |
| Уровень не меняется сам | добавить XP до порога | уровень остался прежним, на листе видна готовность |
| Выдача предмета по UUID из компендиума | `POST` выдачи | предмет в инвентаре с исходным UUID |
| Хуки | подписка SSE, правка листа в Foundry | событие приходит за секунды |
| Работа без браузера GM | безголовая сессия | запросы проходят, сессия переживает сутки |

Пример проверки (curl, форма запроса из документации relay):

```bash
curl -s "http://localhost:3010/structure?clientId=$CLIENT_ID&types=Actor" \
  -H "x-api-key: $FOUNDRY_API_KEY" | jq '.'
```

Если хотя бы две из трёх проверок «монеты / идемпотентная запись / стабильность безголовой сессии» провалены, переходим к варианту Б — собственному модулю **Foundry Bridge** (тонкий модуль с тем же портом `FoundryGateway`, всё остальное приложение не меняется).

### 2.7. Кто чем владеет

Foundry владеет состоянием листа, приложение — историей и намерениями. Расхождения не затираются, а записываются.

| Значение | Владелец | Как меняется | Расхождение |
| --- | --- | --- | --- |
| XP, уровень | Актор Foundry | только задачей интеграции: абсолютное значение и предусловие | запись `external_adjustment`, предупреждение мастеру |
| Монеты | Актор Foundry (монеты как предметы) | задача интеграции | то же; история хранится в журнале |
| Предметы инвентаря | Актор Foundry | выдача и удаление по UUID | сверка со снимком |
| Имя, портрет, родословная, класс, HP, AC, скорость, характеристики, навыки | Актор Foundry | приложение не пишет; зеркало обновляет только синхронизация | триггер БД запрещает любые другие записи |
| Статус, владелец, одобрение персонажа | Приложение | веб и бот | — |
| Свои валюты (репутация, жетоны, ресурсы фракций) | Журнал приложения | проводки | обратная проводка |
| Репутация у фракций, отношения, территории | Приложение | журналы с историей | обратная запись |
| Цены и остатки магазинов, очередь, экспедиции, припасы | Приложение | — | — |
| Статьи и журналы | БД, копии в Obsidian и Foundry | `rev` и хэш | запись конфликта |

Запись «изменить XP или деньги» всегда состоит из двух частей: проводка в журнале (что и зачем) и задача интеграции (применить к актору). Покупка считается завершённой только после подтверждения чтением назад.

### 2.8. Бюджет запросов и кэш

По вашим данным, в бесплатном плане публичного relay — 5000 запросов в месяц. При своём relay такого ограничения быть не должно, но в репозитории relay есть код биллинга ([структура проекта](https://robins-foundry-relay.duckdns.org/docs/contributing)), поэтому Спайк 0 проверяет, что локальный режим запросы не считает. Кэш нужен в любом случае: Foundry на удалённом сервере, а каждый вызов нагружает сессию GM.

1. Игроки читают только снимки из БД (`foundry_actors.snapshot`) и в Foundry не ходят: сколько бы ни было игроков, это 0 запросов.
2. Снимки обновляются по событиям SSE. Резервный опрос — раз в 10 минут и только по изменившимся актёрам (сравнение хэша).
3. Каталог предметов PF2e загружается один раз и обновляется при смене версии системы, а не по запросу пользователя.
4. Одинаковые одновременные запросы склеиваются; чтения журналов кэшируются на 5 минут.
5. Счётчик запросов по дням и предупреждение на 80% квоты, если лимит окажется включён. При исчерпании — режим «только очередь»: записи ждут, чтение идёт из кэша.

### 2.9. Повышение уровня и дополнения к Спайку 0

Когда XP достигает порога, приложение ставит `level_up_pending`, пишет игроку и мастеру в Discord и затем, по подтверждению мастера или автоматически (настройка), добавляет операцию `ApplyLevel` с предусловием «уровень сейчас N» и записью N+1. Вы ожидаете, что после программной смены уровня система оставит места для выбора черт. Как PF2e 8.7.0 ведёт себя в этом случае, я не проверял.

Спайк 0 дополняется проверками:

- поднять уровень тестовому актору через relay и посмотреть лист: появились ли пустые слоты черт, не сломались ли производные значения;
- подтвердить, что self-hosted relay не считает запросы по плану;
- подтвердить, что WebDAV-сервер отдаёт `ETag` и принимает `If-Match` (3.6);
- выгрузить образцы журналов Campaign Codex (3.2).
