# Процесс разработки

1. Сначала `AGENTS.md`, `pad.yaml`, `.agent/README.md`, состояние и назначенная задача. Сверить их с Git; не полагаться на чат.
2. Найти полный источник в `.agent/context/DOCUMENTATION.md`. Сводка не заменяет раздел и SQL. Сначала прочитать связанные требования, ADR, открытые вопросы и соответствующие таблицы/триггеры.
3. Двигаться по этапам 0–11 без вырезания функций: [roadmap](roadmap.md). В каждом этапе: **миграции + тесты БД → API + curl → команда бота → интерфейс**. Упоминание UI не означает перенос всей работы на frontend.
4. Этап 0 проверяет интеграционные гипотезы, не пишет в чужой мир без разрешения. Если условие fallback из плана выполнено — спроектировать Foundry Bridge с тем же портом, не менять остальной продукт молча.
5. Формализовать результат задачи: scope, owned files, зависимости, критерии и точные команды проверки. Несогласованные продуктовые решения оформить вопросом; не превращать их в принятое ADR.
6. DB-инварианты не дублировать иначе в сервисе: приложение добавляет identity/permissions/CanSee и расчёты, которые исходник оставляет сервису. Секреты не в документации и не в логах.
7. После SQL-изменений регенерировать DBML, ER и каталог. Изменение API/версий/прав требует согласования согласно `pad.yaml`.
8. Запустить `scripts/validate_artifacts.py`, генератор с `--check`, затем соответствующие SQL/API/UI проверки. Отсутствующую сборку или недоступную интеграцию честно указать; не записывать ложный PASS.
9. Завершить обновлением статуса задачи, `.agent/state/current.yaml` и единственного HANDOFF. Параллельные агенты работают по существующим PAD-протоколам, не создают конкурирующие состояния.

## Теперь и после реализации

Сейчас воспроизводимы проверки артефактов и baseline БД. `docker compose up -d`, Go-сборка, frontend, goose и live-интеграции в плане — **целевые**, не доступные команды этого репозитория. Импорт не создаёт пустые сервисы ради видимости готовности.
