# Актуальный статус реализации

Исходные этапы 0–11 и их продуктовый смысл сохраняются. Технические задачи можно переставлять с учётом зависимостей, не теряя acceptance criteria. Небольшие вертикальные задачи не закрывают этап целиком.

## Обязательная архитектурная граница Foundry

[ADR-0003](../../.agent/decisions/ADR-0003-foundry-authority-and-read-only-relay.md) — действующее решение владельца и имеет приоритет над противоречащими формулировками импортированного плана ниже.

- Foundry — единственный источник истины для Actor sheet data и PF2e mechanics.
- Relay используется для чтения и синхронизации. Приложение не записывает XP, уровень, валюту/монеты, характеристики, способности, HP, AC, навыки, класс, родословную, предысторию, ownership/permissions, flags или любые произвольные поля Actor.
- Единственное исключение — GM-authorized add/remove Item на существующем Actor (снаряжение, способности и другие Foundry Items). Оно реализуется только отдельным узким flow TASK-019.
- Item write требует серверной проверки GM permission, стабильных Item identifiers, отдельного write credential, operation ID/idempotency, audit, безопасной обработки timeout и read-back из Foundry. Никакого generic Relay write proxy.
- Любые ручные изменения в Foundry должны попадать в приложение через sync; приложение не перезаписывает источник.
- Данные, принадлежащие самому приложению (заявки, приключения, репутация, экспедиции, магазины/ledger и т.п.), продолжают изменяться в PostgreSQL согласно собственным правилам доступа. Это не даёт права писать в Foundry.

## Ближайший план разработки

1. **TASK-014 — стабилизация Production:** обратная связь игроков, проверка backup schedule, тестовое восстановление в отдельную БД, мониторинг RAM/OOM/disk/logs. Не менять существующие проекты/сервисы.
2. **TASK-015 — Foundry Item search:** read-only поиск по Actor/Compendium Items через Relay, фильтры, пагинация, traits/rarity/price, корректное различение Actor Items и Compendium references.
3. **TASK-016 — NPC Discord webhooks:** GM-only отправка сообщений от имени NPC, динамические имя/аватар, allow-list каналов, защита credentials, audit и тестовый канал.
4. **TASK-017 — первый релиз:** GitHub Actions Release, Conventional Commit grouping, SemVer validation, prerelease tag `v0.2.0-beta`. Релизная линия — `v0.2.0`.
5. **TASK-018 — сервер и безопасное обновление:** проверка нового сервера, immutable image SHA, health/readiness, backup, rollback. Автоматический Production CD остаётся выключенным до прохождения gate и отдельного подтверждения владельца.
6. **TASK-019 — GM Item add/remove:** после поиска и проверки Foundry adapter реализовать узкую запись Item по ADR-0003. Не расширять её до записи других Actor полей.

Параллельно продолжать полные этапы 0–11 по исходному scope. Вертикальные задачи 015/016/019 не означают закрытия TASK-004 или этапа 2.

## Release policy

- Первый релизный номер: **`v0.2.0`**, prerelease tag **`v0.2.0-beta`**.
- Conventional Commits уже закреплён; GitHub Actions Release ещё не реализован.
- Release automation не включает Production CD.
- CD заблокирован до TASK-014/TASK-018 и явного owner approval.

## 9. План этапов

Порядок внутри каждого этапа одинаков: сначала миграции и тесты БД, затем API с проверкой через curl, затем команда бота, и только после этого интерфейс. Этап закрывается, когда выполнены его проверки. Сроков я не ставлю: они зависят от вашего времени.

Порядок отличается от ТЗ в двух местах: добавлен Этап 0 (спайк), а экспедиции и фракции стоят после карт, календаря и погоды, на которые опираются, и перед торговым предприятием.

| Этап | Состав | Проверки | Готово, когда |
| --- | --- | --- | --- |
| 0. Спайк (1–2 дня) | relay у вас на хосте; чтение листа PF2e; монеты как предметы; хуки SSE; безголовая сессия; лимит self-hosted relay; ETag и `If-Match` на вашем WebDAV; выгрузка журналов Codex (read-only) | пункты из 2.6, 3.2, 3.6; для каждого — результат и вывод | есть решение «relay или собственный модуль» и образцы данных Codex |
