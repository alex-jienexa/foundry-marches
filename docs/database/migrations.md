# Правила миграций

## Сейчас

`docs/database/schema.sql` — baseline v0.3 для **пустой** БД. Исходник не является goose-миграцией, не идемпотентен и не содержит безопасного `Down`. Повторное применение на рабочей БД запрещено. При импорте DDL не менялся.

## Этап 1 (предлагаемый процесс)

1. Создать инфраструктуру миграций goose в задаче TASK-003. Версии Go/goose и каталог миграций закрепить там; не выдавать документацию за уже существующие команды.
2. Первая forward-only миграция должна воспроизводить весь baseline: domain/extension, таблицы, поздние FK, функции, статические и динамические триггеры, автоматы и seeds. PL/pgSQL и DO-блоки обрамить `-- +goose StatementBegin` / `StatementEnd`, проверить транзакционность выбранной версии.
3. Установку `btree_gist` выполняет уполномоченная роль. Runtime-роль не должна иметь DDL/владение таблицами; `app.writer` — маркер доверенного кода, не механизм авторизации пользователя.
4. В свежих БД PG15 и PG16 сравнить мигрированную структуру с baseline (schema-only dump с нормализацией служебных различий), выполнить 166 тестов и 9 проверок гонок.
5. Только после подтверждения эквивалентности выбрать авторитетный путь bootstrap: миграции; `schema.sql` оставить проверяемым snapshot. Пока такой перенос **не сделан**.
6. Последующие миграции добавлять новыми файлами, не переписывая применённые. Опасные изменения и изменение публичного API — после согласования по PAD.
7. Применение при старте (как в исходном плане) — одним контролируемым migrator/lock, не одновременно API и worker. Runtime-команды не должны получать повышенные права.
8. Перед production: резервная копия и проверенное восстановление; для необратимого изменения — согласованный план восстановления, а не фиктивный откат DROP.

## Проверка baseline вручную

Только в отдельной пустой тестовой БД:

```bash
psql -X -v ON_ERROR_STOP=1 -d "$PGDATABASE" -f docs/database/schema.sql
psql -X -v ON_ERROR_STOP=1 -d "$PGDATABASE" -f tests/database/schema_tests.sql
bash tests/database/schema_race_tests.sh
```

Все три команды должны использовать одинаковые `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`; примеры настройки — в тестовом README. Функциональные тесты и гонки создают и меняют данные, не запускать их на кампании.
