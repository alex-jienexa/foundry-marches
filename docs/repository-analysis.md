# Анализ архитектуры репозитория и адаптация артефактов

## Основа анализа

Публичный репозиторий: https://github.com/alex-jienexa/foundry-marches . Проверенный snapshot ветки `main`: `3032d2da61c090bde83887f564f9487d1e99e27e` (получен 2026-11-17). Изменений в GitHub не выполнялось. Входной архив содержит ровно четыре файла: Markdown-план v0.3, schema.sql, schema_tests.sql, schema_race_tests.sh.

## Что было в репозитории

Это **PAD project starter**, а не архитектурный каркас приложения:

- `AGENTS.md` — обязательный вход и ограничения полномочий.
- `pad.yaml` — проект, autonomy controlled, запрет remote push, управление шаблоном.
- `.agent/` — роли IMPLEMENTER/INTEGRATOR/REVIEWER, протоколы, контекст-заглушка, требования/задачи, ADR, схемы метаданных, единственное состояние/HANDOFF.
- `TASK-001` — заполнить контекст и проверить воспроизводимость, не реализация приложения.
- `.github/workflows/ci.yml` — только проверка наличия нескольких PAD-файлов.
- `.pad-template.yaml` и `.pad/template-base/` — механизм three-way обновлений, а не дубликат актуальной документации.
- Отсутствовали `src/`, бизнес-документация, SQL, миграции, Go/JS-модули приложения и команды сборки.

Следовательно, задача — не рефакторинг runtime-архитектуры, а перенос **полной проектной спецификации** в уже существующую систему долговременного контекста.

## Оценка предложенной структуры

Структура `docs/ + .agent/ + src/` подходит. Она разделяет полные артефакты и краткий контекст агента. Важные корректировки:

1. **Сохранён `schema.sql` как основной DDL.** Один DBML не передаст 51 функцию, 50 явных CREATE TRIGGER, DO-блок с динамическими триггерами, 21 ALTER, специфические индексы/исключения и seeds. DBML добавлен как производное, не замена.
2. **Исходные тесты вынесены в tests/database**, не спрятаны среди reference. Все 166 проверок и 9 конкурентных проверок доступны для CI; оригиналы также сохранены.
3. **Оригиналы в собственных форматах:** Markdown/SQL/Bash, а не вымышленные PDF/DOCX из примера структуры. Побайтовая сохранность — manifest SHA-256.
4. **Архитектура не сведена к overview/components:** добавлены полные foundry, obsidian, states, expeditions, factions, review; аудит схемы — database/design. Все разделы исходника распределены без сокращения, с машинной картой покрытия.
5. **ADR имеют единственный дом:** `.agent/decisions/`. `docs/architecture/decisions/README.md` — указатель и место возможных исследовательских материалов, не второй журнал решений.
6. **OpenAPI не выдуман:** есть `docs/api/README.md`, но нет ложного полного `openapi.yaml`. Примеры curl сохранены в полных разделах; контракт появится из реализации.
7. **src не наполнен фиктивными сервисами:** пока только README о будущих границах. Ни Go, ни frontend, ни bot, ни Compose не объявлены реализованными.
8. **PAD не переинициализирован:** оригинальные protocols/agents/schemas и upstream baseline сохранены. AGENTS дополнен project-specific навигацией; controlled/no-push политика сохранена.

## Целевая архитектура продукта (из плана)

Модульный монолит Go (chi/pgx/sqlc), API и worker — один бинарь, разные команды; отдельный bot discordgo; PostgreSQL 15+ и River; SolidJS/TypeScript/Vite; Caddy/Compose/goose; существующий WebDAV и удалённый Foundry через self-hosted relay. [Полные детали](architecture/overview.md), [границы модулей](architecture/components.md).

Существенные архитектурные границы, которые нельзя потерять при реализации:

- Foundry владеет состоянием листа; приложение — историей и намерениями. XP/монеты/предметы меняются через integration job; расхождения становятся external_adjustment.
- River не заменяет integration_jobs, NOTIFY не заменяет durable event_outbox.
- Wiki/Obsidian/Foundry синхронизируются через БД, rev/hash и ETag, а не по времени файла и не напрямую.
- CanSee и RBAC на сервере; скрытые сведения не должны попадать в payload игрока.
- Экспедиции, фракции и торговое предприятие — полные домены, а не optional post-MVP. Все этапы 0–11 сохранены, включая расширенные функции с исходным приоритетом.

## Навигация агентов и трассировка

Вход: AGENTS → PAD → state/HANDOFF → PROJECT → DOCUMENTATION → полные источники по задаче. ARCHITECTURE/DATABASE/DEVELOPMENT — сводки с прямыми ссылками, не урезанные спецификации.

- TASK-001 — закрытый bootstrap контекста и доступных проверок.
- TASK-002…013 — этапы 0…11. Все 12 этапов ещё не реализованы; dependencies и acceptance criteria связаны с полным планом.
- FM-REQ-001…012 — этапные требования `proposed`, с полными строками состава/проверок/готовности из плана, а не новыми решениями владельца.
- FM-REQ-013 — согласованное требование сохранности артефактов.
- ADR-0002 — только организация артефактов по запросу владельца. Не объявляет утверждёнными ответы на десять продуктовых вопросов.

## Проверяемость и ограничения

[Фактические результаты](verification.md): исполнение исходной схемы/тестов на PG15 и PG16, целостность/ссылки, AST-проекции, синтаксис DBML/Mermaid. GitHub Actions подготовлен, но удалённо не запускался этим импортом.

[Source gaps](development/source-gaps.md): отсутствует само ТЗ v1.0/дополнения, архитектурная картинка заменена маркером в исходнике, API ещё не зафиксирован, live-интеграции и правила путешествий требуют проверки. Ни одна неопределённость не замаскирована под готовое решение.

## Влияние на дальнейшее обновление PAD

`.pad/template-base/` остаётся побайтовой базой прежней версии шаблона. Свою документацию и customizations в AGENTS/.agent/pad обновлять three-way согласно существующему протоколу. Не зеркалировать их в baseline, иначе потеряется возможность отличить upstream-изменения от проектных.
